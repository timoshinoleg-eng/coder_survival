## 5 WHYS АНАЛИЗ ДЛЯ КАЖДОГО P0

### C-001: Stars fulfillment отсутствует (`routes/shop.js` — нет `/buy`)

**Симптом:** `routes/shop.js` содержит только `GET /products` (11 строк). Нет `/buy`, нет обработки `pre_checkout_query`, нет `fulfillment`, нет зачисления товара. (`routes/shop.js:1-11`)

| # | Почему? | Ответ |
|---|---------|-------|
| 1 | Почему монетизация Stars не работает? | Нет endpoint `/buy`: сервер не принимает входящие платежи |
| 2 | Почему нет `/buy`? | `routes/shop.js` реализован как read-only каталог — `/products` для отображения в UI |
| 3 | Почему только read-only? | Реализация payment flow Telegram Stars требует webhook-обработки `pre_checkout_query` и `successful_payment` — отдельный класс сложности от CRUD |
| 4 | Почему webhook не реализован? | Telegram Stars API требует регистрации бота с платёжным провайдером и тестирования в sandbox. Инфраструктура не была настроена |
| 5 | Почему инфраструктура не настроена? | MVP-план отложил монетизацию на «следующий этап», не заложив Stars-интеграцию в acceptance criteria |

**Корневая причина:** Telegram Stars payment flow не был включён в MVP acceptance criteria как блокер. `shop.js` создавался как UI-заготовка.

**Исправление:** Реализовать `POST /api/shop/buy` → Telegram Bot API `answerPreCheckoutQuery` → `successful_payment` webhook → `applyReward(userId, productId)`.

---

### C-002: `featureFlags: {}` блокирует `high_stress` оффер

**Симптом:** `tap.js:192` — `featureFlags: {}` передаётся в `computeContextOffer`. `offers.js:94` — `stressV2 = signals?.featureFlags?.stress_v2 === true` → всегда `false`. `offers.js:100` — порог депрессии всегда `55` вместо `20`. (`balance.js:25` — `depressionThreshold: 55`)

| # | Почему? | Ответ |
|---|---------|-------|
| 1 | Почему `high_stress` оффер не срабатывает при депрессии 20-54? | В `offers.js:94` флаг `stress_v2` никогда не `true` — порог остаётся 55 |
| 2 | Почему флаг всегда `false`? | `tap.js:192` передаёт `featureFlags: {}` — пустой объект жёстко закодирован |
| 3 | Почему `featureFlags` захардкожен пустым? | Feature flags система была добавлена в `balance.js:136-143` как конфиг, но transport layer не обновлён |
| 4 | Почему transport layer не обновлён? | Разработчик добавил `STRESS_V2` конфиг и `AB_TEST_PERCENTAGE: 50`, но не добавил логику «включить флаг для 50% пользователей» в tap-route |
| 5 | Почему логика распределения не добавлена? | Нет A/B testing инфраструктуры (user-level feature flag assignment). Задача была помечена как «TODO: implement feature flag assignment» |

**Корневая причина:** `STRESS_V2` создан как конфигурационная заготовка, но A/B routing (какие пользователи видят `stress_v2 = true`) не реализован. `tap.js:192` — единственный callsite — никогда не обновлялся.

**Исправление:** В `tap.js` добавить `const stressV2Enabled = (userId % 100) < STRESS_V2.AB_TEST_PERCENTAGE` → передавать `featureFlags: { stress_v2: stressV2Enabled }`.

### C-003: Пассивный decay депрессии мёртв (`featureFlags: {}`)

**Симптом:** `balance.js:139` — `DEPRESSION_PASSIVE_DECAY_PER_HOUR: 5` определена. Нет evidence что `progression.js` или `tap.js` читают эту константу при наличии `stress_v2 = false`.

| # | Почему? | Ответ |
|---|---------|-------|
| 1 | Почему депрессия не восстанавливается пассивно? | `stress_v2` никогда не активен → ветка с passive decay не выполняется |
| 2 | Почему ветка с passive decay не выполняется? | Тот же root cause что C-002: `featureFlags: {}` в `tap.js:192` |
| 3 | Почему passive decay привязан к feature flag? | `STRESS_V2` задуман как A/B тест — только 50% игроков должны видеть новую механику |

### C-008: Математика пасса: 49 дней при 30-дневном сезоне

**Симптом:** `balance.js:196-251` — `STAGE2.PASS.LEVELS`: суммарно 11 500 XP (`console.assert` подтверждает). `computeTapXp` (Junior) = 1 XP/тап. 120 тапов/день + квесты ≈ 235 XP/день → 49 дней.

| # | Почему? | Ответ |
|---|---------|-------|
| 1 | Почему пасс нельзя пройти за 30-дневный сезон? | 11 500 XP при 235 XP/день = 49 дней. Нужно 7 000 XP для 30 дней |
| 2 | Почему суммарный XP = 11 500? | `STAGE2.PASS.LEVELS` = арифметическая прогрессия: level i = 100 + (i-1)×50. Сумма 20 уровней = 11 500 |
| 3 | Почему выбрана такая прогрессия? | Документ 4, Раздел 0.3 цитирует другой `SPRINT_PASS_LEVELS` (с общей суммой ~865 XP) — который теперь dead code |
| 4 | Почему активен более тяжёлый конфиг? | Рефакторинг Stage 2 добавил `STAGE2.PASS.LEVELS` без удаления `SPRINT_PASS_LEVELS`. `console.assert` на 11 500 подтверждает какой из них активен |
| 5 | Почему `SPRINT_PASS_LEVELS` не был удалён? | Технический долг рефакторинга: нет тестов, проверяющих какой конфиг читается. Неясно что старый конфиг стал dead code |

**Корневая причина:** Два конфига пасса в одном файле с несовместимой математикой. Более тяжёлый (`STAGE2`) активен. `SPRINT_PASS_LEVELS` — dead code но создаёт confusion.

**Исправление:** 1. Удалить `SPRINT_PASS_LEVELS`. 2. Пересчитать `STAGE2.PASS.LEVELS` до суммы ≤7 000 XP (30 дней × 235 XP/день). 3. Обновить `console.assert`.
